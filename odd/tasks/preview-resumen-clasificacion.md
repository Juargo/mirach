# Upload preview — classification summary (accordion)

Objective: on the upload preview (screen 04, state `decidiendo`), show how the statement was auto-classified as a three-level accordion (bucket → category → movement) with counts and money totals, then let the person choose «Subir tal cual» or «Revisar y editar». Branch `feat/preview-resumen-clasificacion`. Delivery: chained PRs stacked to main, one per unit (the user's cached choice): API → iOS → Android. Test runners: API `pnpm api test` (vitest); iOS `xcodebuild test -only-testing:MirachTests` from `apps/ios`; Android `./gradlew :app:testDebugUnitTest` from `apps/android`.

## Specs

- **S1 — Summary of automatic classifications on the preview.** The preview screen shows "un resumen de las clasificaciones automáticas y que dentro de eso pida si quiere editar algo o subir tal cual" (L1). The existing `decidiendo` actions stay: «Subir tal cual», «Revisar y editar», «Descartar». The summary is read-only: tapping a movement does nothing in this version (assumption, from L1: editing goes through «Revisar y editar»).
- **S2 — Shape: three nested accordions.** "Bucket en acordeon y dentro del acordeon categoría en acordeon y dentro de la categoría el item de transacción" (L2). Level 1: one row per bucket (Necesidades, Gustos, Ahorro; the API still names Gustos `Deseos`) with movement count and total. Level 2, inside a bucket: one row per category with count and total. Level 3, inside a category: the movements (date, description, amount) in `rowIndex` order. Income rows (`abono > 0` and `cargo == 0`) are listed under their own «Ingresos» header with count and total, outside the buckets, as on screen 24. Duplicates (`esDuplicado: true`) are excluded from the groups; the existing «duplicados» counter already reports them. Assumptions: buckets appear in the fixed order Necesidades, Gustos, Ahorro and only when they have movements; categories inside a bucket are sorted by total descending; everything starts collapsed.
- **S3 — The API computes the grouping (additive contract).** `POST /api/ingestas/preview` adds `resumen.clasificacion`, optional on the wire (the server always emits it; a client treats its absence as "no summary", so a new build works against a server that predates the field; see L8 for why shipped iOS builds still break on any new key): `{ "ingresos": { "cantidad": n, "total": "<decimal string>" }, "buckets": [ { "bucket": "Necesidades" | "Deseos" | "Ahorro", "cantidad": n, "total": "<decimal string>", "categorias": [ { "categoriaId": "<id>" | null, "nombre": "<name>", "cantidad": n, "total": "<decimal string>", "filas": [rowIndex, ...] } ] } ], "desconocidos": n }`. Money totals use the same BigInt-safe decimal string convention as `abono`/`cargo`; `total` of a bucket or category is the sum of `cargo` of its rows; `ingresos.total` is the sum of `abono`. `desconocidos` counts the rows whose suggested category is the account's «Desconocido» default (CLA-13). Rows with `esDuplicado: true` are excluded from every group and count. Rationale (project rule): business calculations and money sums live in the API; clients are thin and render what they receive. `openapi.json` is regenerated and both clients regenerated from it.
- **S4 — Highlight the unknowns.** Above the accordion the screen states how many movements fell into «Desconocido»: «N movimientos quedaron en Desconocido» when `desconocidos > 0`, or a line saying everything was classified when it is 0 (exact copy decided in the client task and recorded in the Log). When `desconocidos > 0`, «Revisar y editar» becomes the primary button and «Subir tal cual» the secondary one; otherwise the current order stays (assumption, from L1: the summary exists to answer "¿subo o reviso?").
- **S5 — Catalog (docs).** `docs/catalogo/flujos/subir-cartola.md` describes the new content of screen 04 and the `resumen.clasificacion` contract; the screen row keeps its Figma node until the owner updates the design (the Figma update is the owner's, outside this feature's code).
